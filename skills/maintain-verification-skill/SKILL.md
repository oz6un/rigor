# Maintain a verification skill

Other skills named here don't appear in the model's skill list. To use one, read `<this skill's dir>/../<name>/SKILL.md` (with symlinks in this skill's path resolved) and follow it.

A feature map goes stale as the app changes. This skill keeps a skill generated by `create-verification-skill` (or any project-local verification skill with a feature map) accurate. The unit of coverage is the feature: every feature file gets read against source and driven live, but you don't need to execute every bullet.

## Outcomes

End with exactly one, and say which:

- **clean**: every feature got source and live coverage and nothing needs changing. No branch, no PR.
- **changed**: one PR of proven corrections to docs, harness, or map.
- **blocked**: coverage couldn't finish, or a proven fix couldn't ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory: its `SKILL.md`, `features/`, and any harness scripts it owns. Don't edit product code during a run. When the map describes behavior the app no longer has, it's either doc drift (fix the map) or a product regression (report it; don't rewrite the docs to match the bug).

## Pass

1. **Locate the target.** Find the project-local skill with launch and drive sections and a feature map, usually `.agents/skills/verify-*/` (linked from `.claude/skills/`). If there are several, ask the user which. If there are none, stop and point at `/create-verification-skill`.

2. **Index hygiene.** Read `features/README.md` and list its sibling files. Fix missing, extra, duplicate, or dead entries.

3. **Source pass.** Spawn one read-only subagent per feature file, all in parallel (Claude Code: `Explore` agents; Codex: `rigor-reviewer`). Each explains how the feature works from source, flags likely drift with file citations, and returns one concise live-verification recipe. Subagents never drive the app or edit files. Return shape: feature summary, source entry points, likely drift (or none), one recipe.

4. **Reconcile.** Confirm every feature file got a summary. Merge overlapping recipes so the live pass needs as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Check recent commits for user-facing surfaces missing from the map, and require a concrete source path before calling one missing.

5. **Live pass.** Required even when the source pass looks clean. You (the coordinator) do all driving. Follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. Drive every feature at least once. Hold these invariants throughout, whatever fails:
   - Don't drive an instance you haven't health-checked since it last did something unexpected. Run doctor before the first drive, on each fresh session where sessions are the unit, and after any failed drive. When doctor can't see the problem (a stuck UI on a healthy process), reset to a known state or relaunch.
   - Evidence captured so far survives every cleanup. Check it at its named location.
   - Nothing a drive started outlives its use. Clean up after failed iterations whether the session is stuck, exited, or shared. For a shared instance, clean the leftovers, not the instance.

   A doctor failure caused by the skill being out of date is drift: fix it within edit scope and retry once, restarting only what the fix invalidated, before calling the pass `blocked`. Mark a feature `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route you tried. If the map doesn't mention that prerequisite, that's drift too. Re-drive any harness fix live before it ships. Do the final teardown after the last drive, including those re-drives; evidence stays.

6. **Triage.** Wrong or missing user-facing description: doc drift, fix it. Working behavior the harness can't drive: harness gap, fix it (scripts executable, invocation documented in the skill body). App behavior that's broken: product gap, report it to the user and keep it out of this PR.

7. **Ship or stop.** For `changed`, open one PR of proven corrections through the rigor skill's `playbooks/opening-a-pr.md`, after re-reading every changed file. For `clean` or `blocked`, open no PR; report the outcome and coverage.

Keep short run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location outside the repo. Don't commit them.
