# Orchestrate

You own the program, not the code. You write briefs, drain the queue of finished work, keep the bottom of the stack green, and make the judgment calls.

Use this for a project handed to one standing coordinator session: multi-day, many stacked PRs, dozens to hundreds of subagents, the user checking in a couple of times a day. One task driven to a predicate is Autonomous run; one ambitious run needing its own workflow is `figure-it-out`. If one agent could finish within the session's budget, it isn't a program. For cheap, near-identical units, collapse the process as each section describes.

Three rules:

- A finished subagent is a queue event, not an interrupt. Record it and keep going.
- Every spawn and every resume carries the standing orders word for word.
- The brief is your product. A worker can't ask you questions, so a vague brief fails without anyone noticing.

The [shared program rules](#shared-program-rules) at the end of this file (operator gates, wake mechanics, liveness, forge, verification rounds) also apply to the Autopilot playbooks.

## Roles

- **Coordinator (this session).** Frames the program, writes briefs, drains the inbox, writes the user's reports, and makes judgment calls. It doesn't write or edit code: conflicted merges, restacks, and code changes are all tasks for workers. On repos where local git is cheap it may land verified work itself (fast-forward or clean cherry-pick, then push), so verified units don't queue behind a busy stacker. It reads and writes state only through `orch` (see [Store](#store)) at drain points; `orch` never spawns, waits, or wakes anything.
- **Sub-coordinator.** One per track, and only when the program is larger than one coordinator's drains can handle. Each extra layer pays its own orientation cost, and a blocking sub-coordinator hides its children while the parent idles. It owns its track's units, writes its workers' briefs, spawns its workers and verifiers, and reports aggregates at wave boundaries, not raw child reports. It keeps at most about ten children in flight as a rolling window.
  - Nesting depends on the host. If subagents can't spawn their own subagents, run each sub-coordinator as its own top-level `claude` or `codex` session in its own worktree, or have the coordinator absorb the track.
- **Worker and verifier.** Each writes in its own worktree or branch, one writer per worktree or branch (the `separate-before-serializing-shared-state` principle). In Claude Code, spawn with `isolation: "worktree"`; in Codex, create the worktree with `git worktree add` and name it in the brief. Prefer fewer, broader workers. Run a unit's verifier on a different model from its worker (another host model, or the other CLI via `<rigor skill dir>/scripts/second-opinion.sh`).

Keep the depth at coordinator, track, worker. Choose tracks per project; build, landing, and verification are common splits.

## Store

Create the store outside the repo, for example `~/.rigor/orchestrate/<project-slug>/`, and export `ORCH_STORE` to it. Every file has one writer. Do bookkeeping with `<rigor skill dir>/scripts/orch/orch` from the rigor skill's directory (written `orch` below); its TSV and JSON stay readable without it.

| File | Contents |
|---|---|
| `preferences.md` | Standing orders: numbered lines, one constraint each (model policy, stack shape, verification bar, forbidden paths, escalation). Instructions get lost across resumes, so paste this into every spawn and resume. When you catch yourself restating an instruction, add it here first (`encode-lessons-in-structure`). |
| `overview.md` | Durable PR and issue record. Append only. |
| `units.tsv` | One row per unit: id, track, state, branch, PR, head SHA, brief path. Updated in place. |
| `frontier.json` | The computed merge frontier (see [Stack safety](#stack-safety)). |
| `ledger.tsv` | The verification ledger (see [Verification](#verification)). |
| `inbox/` | Completion pointers. |
| `gates.md` | Decisions parked for the user (question, options, default). `orch gate park`. |
| `decisions.tsv` | The decision log, per the `show-me-your-work` skill. |
| `status.md` | Generated by `orch status` at each drain. Never hand-edited. |

## The brief

Every spawn gets a complete brief. If you can't fill a field, the unit isn't scoped yet.

```
GOAL         one sentence stating the outcome, doable by someone with no access to this conversation
SCOPE        paths this unit may write; paths it may not; its own worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers can't see their siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-skill steps, plus known gotchas
TIMEBOX      rough runtime cap; when it expires, return partial findings and stop
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups
STANDING     <preferences.md pasted verbatim>
```

- Size the brief to the unit. A one-command unit gets a paragraph naming goal, scope, verify command, and report shape. Standing orders may go by store path to an agent that can read the store; resumed agents get them pasted.
- A sub-coordinator's brief adds its track boundary and units, spawn budget, the drain protocol, and the rollup format (per child: name, status, PR, head SHA, verdict, one line; plus track status and frontier change).
- A dependency passes context, not just ordering. Don't spawn with fields missing.
- Once per wave, audit one sampled worker brief per sub-coordinator, alongside the wave rather than gating it. On failure, stop that track and fix the sub-coordinator's instructions; brief quality decays late in a run.
- Don't extend a brief by resuming an agent. Spawn fresh with the consolidated scope.

## Steps

1. **Frame.** State the done predicate as something countable ("all 126 units merged, each with a ledger verdict of `unit-test-verified` or better"). Estimate units, effort, expected stacks, and the wall-clock budget. If one agent could finish within that budget, switch to Autonomous run: work in this session, verify inline, land as you go, and skip the store and pilot. Plan landing against the budget: by about 70% of it, stop spawning and land what's verified. Name the tracks. Run a contested split or a one-way decision through the `arena` skill before the pilot. Present the framing to the user once, and continue with reversible prep without waiting.
2. **Set up the store.** Run `orch init`. Start the decision log per `show-me-your-work`, write the standing orders before any spawn, and seed the frontier from existing PRs with `orch frontier set --repo <repo-dir>`.
3. **Pilot.** Take one unit through the whole path: brief, worker, verification, stack entry, ledger row, merge. It tests the brief template, verify recipe, and unit size while a mistake costs one agent instead of fifty; fix them before fanning out. For near-identical cheap units, the first unit is the pilot, run normally, and fan-out starts when it lands. Keep the full pilot (separate verifier, brief audit) for expensive or novel units.
4. **Scale.** Keep a rolling window of workers up to the in-flight cap, refilling as they finish. Add sub-coordinators only past the threshold in [Roles](#roles). After each drain, recompute ready work and pass upstream reports into downstream briefs; siblings communicate only through you. A failed brief audit stops the next refill, not the wave already running.
5. **Drain.** Follow [Queue and drain](#queue-and-drain) at every drain point.
6. **Land.** Landing starts with the first verified unit and runs alongside later waves. On heavy repos the stacker is a standing role from wave one; where local git is cheap, the coordinator lands. Keep the frontier green before building more on top of it. Advance `frontier.json` only on a merge or a reported new head SHA.
7. **Close.** Drain the last of the inbox. Give every spawned agent a terminal row (done, abandoned, or reconciled). Confirm the predicate on the real artifact, and confirm every landed PR has a verdict for its current head SHA. Review the decision log per `show-me-your-work`, including its cross-model review. Move recurring corrections into `preferences.md` or the brief template. Leave the store in place as the postmortem record.

## Queue and drain

- When a subagent finishes, run `orch inbox push <agent> <unit> <status> [--report PATH]` and go back to what you were doing. Don't review its work inline; if it needs review, that's a verifier unit.
- Drain in batches at four points: after finishing a critical section, at a track rollup, when a frontier watcher wakes you (the `/goal` check-ins cover a watcher that dies silently), and before a report to the user. Start each batch with `orch inbox drain`. Anything that arrives during a drain waits for the next one.
- Critical sections you finish before draining: writing a brief, a stack operation, a conflict decision, writing a gate, updating the ledger or frontier.
- In each drain, classify every pointer (landed, needs-verify, failed, zombie, noise), record the results with `orch unit add`, `orch unit set`, and `orch ledger record`, run `orch status`, then spawn the next wave in one message.
- At each rollup, account for every spawned child: arrived, respawned, or scope explicitly absorbed. Quietly redoing a missing child's work hides the waste and the gap.
- End a drain turn with the three lines `orch status` prints: counts by state, what changed, and open gates. Details live in `status.md`. Use the full reply at checkpoints and at close.

## Stack safety

- The frontier is computed, not described. After every merge or stack change, recompute `frontier.json` with `orch frontier set` from where `gt` (Graphite) tracks the stack, normally the stacker's clone. GitHub base refs drift during a restack; `gt`'s tracking is authoritative. The frontier holds the ordered PR list, branch names, head SHAs, a generation number, and the lowest unmerged PR. A checkout whose `gt` metadata never saw the submits reports no PRs, and the command errors instead of guessing.
- Exactly one stacker per stack runs `gt`, one operation at a time. Record who holds it in the standing orders. Run restacks in the stacker's own clone or a remote machine; a large local restack can make the laptop unusable.
- Workers never rebase and never run `gt`. Babysitters follow `playbooks/babysit.md`, one per stack, each scoped to one frontier generation. They report conflicts to the stacker instead of restacking.
- Only the stacker closes or retargets PRs, because closing a base PR orphans every PR above it. Merges and stack surgery are units with briefs like any other.
- One retro watcher follows merged PRs for reverts, post-merge CI failures, and orphaned follow-ups.

## Verification

When VERIFY is one cheap command, the worker runs it and reports the output, and the coordinator spot-checks receipts. Use a dedicated verifier (different model from the worker) only when verification is expensive, needs judgment, or has a large blast radius.

Record verdicts with `orch ledger record` and check a PR's current head with `orch ledger check`. `ledger.tsv` has one row per verdict, keyed by PR number and head SHA, with one of these values: `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, `verifier-failed`.

- Green CI is an input to a verdict, not a verdict.
- Behavioral changes need better than `type-check-only`.
- `verifier-blocked` is not a pass; respawn the verifier when the environment is fixed.
- `verifier-failed` gets a fix unit, not a re-verify.
- A worker may record its own verdict; a verifier's row on the same key replaces it.
- A new head SHA voids the row, so re-verify after a restack.
- The ledger is the answer to "was this verified?", not memory or the transcript.

A unit isn't done until its output exists outside the agent that made it, as it lands rather than at the end: pushed branch, ledger row, receipts in the store.

## Failure and recovery

- Probe liveness per [Liveness](#liveness). A subagent that dies silently gets a synthetic postmortem pointer in the inbox (unit, failure mode, last evidence, options). Replan as evidence arrives.
- Retry by failure mode: context or memory exhausted, respawn with a smaller scope; network drop, retry as is; tool error, retry on a different model; unknown, retry once. After two retries, abandon the unit and plan around it.
- Reconcile an agent that reports back hours late against the current frontier and ledger before accepting anything. Salvage unique findings through a fresh unit, never a blind merge.
- If further spawns would all produce bad output (bad upstream result, broken acceptance, broken infra), put a stop line at the top of the standing orders, let in-flight work finish, fix the cause, then remove it.
- Limit your own retries the same way. After a few consecutive tool failures, stop, write a handoff to the store (what's done, where it lives, the exact command to resume), and end the run.
- After the host session restarts, its subagents are gone but pushed branches and PRs remain. Re-read the standing orders and `units.tsv`, recompute the frontier, reattach work by PR and branch, respawn one sub-coordinator per track from its stored brief plus current state, drain, and continue. `orch` replaces a lock whose holder process has exited.

## Escalation

Batch these into the status report rather than asking one at a time: irreversible actions (force-pushing a shared branch, deploys, deletions, closing someone else's PR), product or preference calls no experiment can settle, a standing order that contradicts what you observe, and a program-level dead end that survived a replan. Park each with `orch gate park` before asking, and route work around it.

Don't escalate frontier nudges, restack mechanics, retries, CI flake triage, review-thread triage, formatting fixes, scope the brief already forbids (refuse and continue), or "should I keep going?". When in doubt, act and log it.

Mid-run, fix only what blocks the frontier and park everything else as follow-ups. At this fan-out, a small scope leak turns into many PRs nobody asked for.

**Reply:** at checkpoints and at close: the predicate and the count against it (from `units.tsv` and `ledger.tsv`, not narrative), each track and what it landed, the frontier (PR list with SHAs), a summary of verdicts, what was abandoned and why, gates waiting on the user (the only questions), the store path, and the decision-log path. Include PR links.

## Shared program rules

These apply to Orchestrate and to both Autopilot playbooks. In the Autopilots, the coordinator is called the root, and each PR has one owner subagent.

### Operator gates

- **State, then wait.** A request to state the protocol or plan is not a go. Deliver it and stop.
- **Arm the objective on the go.** Write the program objective (plan path, PR ids in order, verification rule, who merges, done condition) to the store. Arm `/goal <objective>` (both hosts) so the session keeps working across turns until done.
- **User-reserved items** stop at merge-ready; the user merges them.
- **Stop means stop.** A hold from the user goes to every owner at once as a zero-writes order; owners keep their briefs until released.

### Forge

Use GitHub through `gh` for every PR operation (create, edit, view, watch, merge). Don't require Graphite (`gt`) outside Orchestrate's stacker role.

### Wake mechanics and the audit tick

The armed `/goal` keeps the session working, in both hosts; don't build your own timer with `/loop` or `sleep`. Run the audit tick on a 30-minute cadence: record the time of each tick in the store, and at the start of every goal turn, run the tick if 30 minutes have passed since the last one. Wait on events (CI, a merge) with a watcher such as `gh pr checks <pr> --watch`, in the foreground or as a background command. In Claude Code, `/goal` also checks in every 30 minutes while background work is running, so a stalled watcher still gets noticed.

At each tick:

1. Re-read the execution playbook and the armed objective, audit the operation against both, and fix drift in this tick.
2. Probe each owner or lane per [Liveness](#liveness) and collect their decision logs.
3. After batched merges, run a retro pass and sweep post-merge review-bot comments.
4. Keep ticking until no delegated work is left, including after the last merge.

### Liveness

- Never resume an agent just to check on it; a resume restarts an idle agent. Probe read-only: the ledger, `units.tsv`, `gh`, pushed branches, and the host's list of running tasks where it has one. A transcript file's modification time doesn't prove the agent is alive.
- Don't wait for every child to go quiet before replanning; act on each result as it arrives.
- Count only side effects as progress: commits, pushes, PR or check changes, reports in the store.
- Every owner keeps a `children.tsv` next to its `decisions.tsv`: one row per subagent with its id, expected runtime (at least the longest previous run of that kind), and state.
- A lane or subagent that errors, or passes its expected runtime without a side effect, is stuck. Stand it down, have its owner record it as stuck, and dispatch a replacement at once if the work is still needed (the root does this when the owner can't). A replacement that stalls gets the same treatment. A stall never proves the work and never drops it.

### Owner lifecycle (Autopilots)

One owner subagent per PR carries it from build through babysit:

1. Within about 15 minutes: push the first branch snapshot, open the PR as ready (not draft) before self-proof, and start `decisions.tsv` (per `show-me-your-work`) and `children.tsv`. Keep both logs uncommitted and return them with each report.
2. Prove the change on the real artifact (the `prove-it-works` principle). This self-proof runs after the code-ready report; see step 7.
3. Triage automated reviewer comments skeptically per the rigor skill's `references/review-bot-triage.md`.
4. Run `deslop`, then `no-comments`.
5. Autopilot (stack) owners skip this step: they never rebase, because the root is the only one that changes the stack's shape. Everyone else: rebase onto current trunk once before the code-ready report, whether or not trunk moved. Keep that merge base during fix rounds. Rebase again only at merge prep, on a `git merge-tree` conflict with trunk, or on a CI failure caused by a change on trunk. Publish a rebase by pushing only the owner's own branch with `git push --force-with-lease`, after checking the remote head with `git ls-remote`. Never force-push a shared branch.
6. Before any push that starts a verification round, run the pre-review checks that the repo's `CLAUDE.md` or `AGENTS.md` files name for the touched paths, on the committed head. A passing hook isn't proof.
7. When the code is final (after `deslop` and `no-comments`), report the code-ready head SHA, and report the SHA of every later push that changes the patch. Self-proof, CI, and babysit (`playbooks/babysit.md`) then run in parallel with the root's verification.
8. Report ready (merge-ready or stack-ready, per the playbook) with the head SHA once self-proof, CI, and babysit have finished.

### Verification rounds

A round starts at an owner's code-ready head SHA and again at each later push that changes the PR's patch. At that SHA, run parallel independent verifiers per the `swarm` skill and combine them into one verdict. Audit the receipts in the owner's ready report before giving the verdict. The lanes:

- **Gates.** Re-run the repo's checks at that SHA.
- **Live.** Prove the change's main behavior on the real surface it touches, with the matching control skill (`control-ui`, `control-cli`) or a named driver where none exists. This lane is required; a verdict without it isn't clean.
- **Regression against trunk.** Run the same key scenario on current trunk. If trunk doesn't have the feature, record that and check the behavior the diff adds plus the end state the user waits for, instead of pretending trunk can produce it.
- **Diff audit.** Two or more review lanes with the full brief, each with one focus (for example consumer parity with trunk, lifetimes and races, data and config safety). Don't trust the PR body.

When the lanes return, send every proven finding to the owner in one fix-forward. A defect a lane filed as a note is still a finding. For each behavior finding, ask for a failing test that covers every site with the same defect, or a repro receipt where no test can show it, and add the defect to the next round's review brief. The new head gets a fresh round and verdict, except lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.

### Countersigns

Raising a pinned gate or budget value (a limit CI only lets tighten) needs the root's fresh countersign, given only after a verifier proves the change. If the user's grant or standing orders cover approvals, the countersign is the approval; the owner records it in the form the tool's approval process accepts, pointing to the countersign, and a lane checks it. The root never gives or bypasses an approval the forge enforces. Absorbing values already on trunk is drift, not a raise.
