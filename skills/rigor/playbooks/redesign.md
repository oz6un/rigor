# Redesign

You own the rethink: a subsystem, or a whole system, rebuilt the way you'd build it today. A designer who has read the code tends to reproduce it, and a rewrite drops requirements only the old code knew. So extract what the system knows, then design without seeing how it does it.

1. **Extract the contract.** Run `how` and `why` over the subsystem and its callers. From their output, the code and its tests, a fresh subagent (so your own design ideas stay out of it) writes what must survive: behavior callers rely on, formats, interfaces, and environment constraints a newcomer couldn't guess. Each requirement states the behavior with its examples and edge cases, then, separately, its evidence and why it exists. It lists separately what looks accidental.
2. **The user prunes the contract.** This sets the new system's size (the `subtract-before-you-add` principle). For each requirement, show who relies on it: callers in code, skills or prompts, and uses recorded in transcripts or logs. Ask about the accidental list and every requirement with no recorded use. Under `/goal` or "don't stop", drop only what's clearly accidental. Then write the kept contract as tests through the entry points callers use.
3. **Design blind.** Run blind seats as in the `arena` skill's Fan out phase for text designs; steps 4 and 5 here replace its later phases. Run each through `<rigor skill dir>/scripts/second-opinion.sh --cli <claude or codex> --cd <empty dir outside the repo, removed after>`, so it doesn't load the repo's instructions (if a CLI is missing, use the other one for that seat). Give it the kept contract's behavior lines word for word, without the evidence, and a brief not to read the code (blindness is by instruction; both CLIs can read the repo). One more candidate reads the code and proposes how to evolve it.
4. **Review the designs.** A fresh reviewer and one on the other CLI check each design against the kept contract and the real environment: which requirement it breaks or misses, and what it wrongly assumes. A finding that names no requirement or observed use is a question for the user (step 2), not a hole to design around.
5. **Decide, then build.** Pick the simplest design that meets the kept contract, with the evolve proposal as the baseline, or keep the current system, still removing what step 2 dropped. To reach it in steps, make each dropped requirement's removal its own commit, then move toward the design as the Refactoring playbook does (`playbooks/refactoring.md`): small behavior-preserving steps with the existing and contract tests as the pin, then proof on the real environment. Only if it can't be reached in steps, build it beside the old version, run the same inputs through both on the real environment (fakes can't show what the old code knew about its environment), take any difference no dropped requirement explains back to the user as in step 2, then cut over and delete the old version. Finish with the Opening a PR playbook (`playbooks/opening-a-pr.md`).

**Reply:** the contract, what was dropped, the reviews' findings, which design won (blind, evolve, or keep) and why, and the evidence that the kept contract held.
