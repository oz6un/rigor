# Redesign

You own the rethink: a subsystem, or a whole system, rebuilt the way you'd build it today. Incremental changes keep every step working, so they can only improve on the current shape; a designer who has read the code reproduces it. A rewrite fails the other way, by dropping requirements only the old code knew. So separate the two: extract what the system knows, then design without seeing how it does it.

1. **Extract the contract.** Run `how` and `why` over the subsystem and its callers. From their output, the code, and its tests, a fresh subagent that hasn't designed anything writes what must survive: behavior callers rely on, data and formats, interfaces, and environment constraints a newcomer couldn't guess. Each item states behavior, not implementation, with its evidence and why it exists. It lists separately what looks accidental, kept only because of how the code is built now.
2. **The user prunes the contract.** Which requirements are real is a product call, and it's where the redesign gets its freedom. Show the accidental list and any requirement worth questioning, and ask. Under `/goal` or "don't stop", drop only what's clearly accidental.
3. **Design blind.** Give two or more fresh designers (new agents, not forks of this conversation) the pruned contract with its evidence removed (file and line references point into the code), each requirement with its reason, and a brief you write: design the system you'd build today, name what it deletes, don't read the existing code. Run one on the other CLI with `<rigor skill dir>/scripts/second-opinion.sh --cd <empty dir> --trace <file>`. The brief is what keeps them blind, so check each trace or transcript for reads of the code. In parallel, one designer who reads the code gives the evolve-what-we-have baseline.
4. **Decide.** Compare the designs against the contract, what each deletes, and its cost against the current system, and say which you choose and why: rewrite, evolve toward the new shape, or keep the current one. To keep, report the contract and stop. To evolve, write the contract tests first and make each pruned requirement's behavior change in its own commit; between those commits, follow the Refactoring playbook (`playbooks/refactoring.md`) with the existing tests and the contract tests as the pin. Steps 5 and 6 are for a rewrite.
5. **Build from the contract, test first.** Turn each requirement into a test at the entry point callers use. Build the new version beside the old one, then run the same inputs through both, on the real environment as well as in tests (fakes can't show what the old code knew about its environment), and diff the outputs. A difference no pruned requirement explains is a requirement the contract missed: add it with evidence, and check the other designs against it.
6. **Cut over and delete the old version** in the same change, with no compatibility layer (the `migrate-callers-then-delete-legacy-apis` principle). Then run the Opening a PR playbook (`playbooks/opening-a-pr.md`).

**Reply:** the contract and what was pruned, the designs and the decision, and the evidence that behavior held: for a rewrite, the parity diff and what the old version knew that the contract had to add; for an evolve, the pin and the real-environment check.
