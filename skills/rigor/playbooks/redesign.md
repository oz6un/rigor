# Redesign

You own the rethink: a subsystem, or a whole system, rebuilt the way you'd build it today. Incremental changes keep every step working, so they can only improve on the current shape; a designer who has read the code reproduces it. A rewrite fails the other way, by dropping requirements only the old code knew. So separate the two: extract what the system knows, then design without seeing how it does it.

1. **Extract the contract.** A fresh subagent that hasn't designed anything reads the code, its tests, its callers, and the git history (`git log -p`; commit messages say why), and writes what must survive: behavior callers rely on, data and formats, interfaces, and environment constraints a newcomer couldn't guess. Each item states behavior, not implementation, with its evidence (a test, file and line, or commit) and why it exists. It lists separately what looks accidental, kept only because of how the code is built now.
2. **The user prunes the contract.** Which requirements are real is a product call, and it's where the redesign gets its freedom. Show the accidental list and any requirement worth questioning, and ask. Under `/goal` or "don't stop", drop only what's clearly accidental and list each drop with how to reverse it.
3. **Design blind.** Give the pruned contract, and only the contract, to two or more fresh designers, one on the other CLI through `second-opinion.sh`, told not to read the code. In parallel, one designer who reads the code gives the evolve-what-we-have baseline. Use `architect` for a module-sized change and `arena` for a large one.
4. **Decide.** Compare the designs against the contract, what each deletes, and its cost against the current system. Rewrite, evolve toward the new shape, or keep the current one; say which and why. A requirement a blind design broke means the contract missed something: add it, with evidence, and check the other designs.
5. **Build from the contract, test first.** Turn each requirement into a test at the entry point callers use. Build the new version beside the old one, then run the same inputs through both, on the real environment as well as in tests (fakes can't show what the old code knew about its environment), and diff the outputs, explaining every difference by a pruned requirement. A test that pins a pruned requirement changes or goes, named in the report.
6. **Cut over and delete the old version** in the same change, with no compatibility layer (the `migrate-callers-then-delete-legacy-apis` principle). Then run the Opening a PR playbook (`playbooks/opening-a-pr.md`).

**Reply:** the contract and what was pruned, the designs and the decision, the parity evidence, and what the old version knew that the contract had to add.
